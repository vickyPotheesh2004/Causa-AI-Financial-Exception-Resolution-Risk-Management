# 2. PROJECT MISSION

Causa is an evidence-driven financial operations system that detects, investigates, risk-assesses, resolves, rejects, or escalates financial exceptions across:

- payments
- settlements
- refunds
- fees
- adjustments
- bank records
- related financial events

The core workflow is:

**DETECT → INVESTIGATE → PROVE → RISK-ASSESS → DECIDE → ROUTE → RESOLVE → VERIFY → AUDIT**

The system must transform:

> "Something doesn't match."

into:

> "Here is what happened, here is the evidence proving it, here is the applicable rule, here is the risk, here is the appropriate decision, here is who must act, and here is whether the resolution was actually verified."

# 4. DECISION MODEL

The system must support exactly these primary decision outcomes:

## AUTO_APPROVE

Use only when:

- required evidence exists
- evidence is sufficiently trustworthy
- no material evidence conflict exists
- all applicable rules pass
- authority is known
- required permission exists
- action is permitted
- risk is within configured limits
- action is safe and idempotent

## REJECT

Use only when the request/case is clearly invalid or prohibited based on evidence and applicable rules.

A failed rule alone must NOT automatically mean rejection.

The system must show:

- decision
- reason
- evidence
- rule
- source
- authority
- action

## FRAUD_ESCALATE

Use when evidence indicates possible suspicious/fraud-related activity requiring specialist investigation.

Do not automatically state:

"this is fraud"

unless an authorized determination exists.

Use language such as:

"Possible fraud; specialist investigation required."

The case must be routed to the configured Risk/Fraud workflow.

## DEPARTMENT_ESCALATE

Use when:

- evidence is insufficient
- evidence conflicts
- authority is unclear
- applicable policy is ambiguous
- manual review is required
- action risk exceeds autonomous threshold
- another department must decide
- external authority is required
- system cannot safely establish the resolution

# 5. UNKNOWN MUST BE FIRST-CLASS

Never force an answer.

The system must support:

- UNKNOWN
- INSUFFICIENT_EVIDENCE
- CONFLICTING_EVIDENCE
- POLICY_UNAVAILABLE
- AUTHORITY_UNKNOWN
- TOOL_FAILURE
- EXECUTION_FAILURE
- VERIFICATION_FAILURE

The rule is:

**No evidence → no confirmed fact.**

**No source → no policy claim.**

**Conflict → no automatic resolution.**

**Possible fraud → fraud investigation.**

**Clear invalid request → reject.**

**All required conditions pass → authorized action.**

**Action completed → verify.**

**Every decision → audit.**

# 9. INVESTIGATION ENGINE

The investigation process must follow:

1. Identify entities
2. Retrieve relevant records
3. Construct financial timeline
4. Calculate expected state
5. Compare expected vs actual
6. Identify discrepancy
7. Collect evidence
8. Check related events
9. Check applicable policy
10. Determine possible root cause
11. Assess uncertainty
12. Produce investigation report

The investigation engine must not hallucinate missing financial records.

If records are missing, explicitly report them as missing.

If records conflict, explicitly report the conflict.

# 20. VERIFICATION

A resolution is NOT complete merely because a department marks it resolved.

After resolution:

1. Re-read relevant financial records.
2. Recalculate expected state.
3. Compare actual state.
4. Validate the correction.
5. Confirm the underlying exception is resolved.

If verification fails:

`RESOLUTION → VERIFICATION_FAILED → REOPEN`

Only successful verification should permit final closure.

```text
→ VERIFIED
→ CLOSED
```

Invalid transitions must be rejected.

Every transition must be audited.
